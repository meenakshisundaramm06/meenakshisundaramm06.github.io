Designer to production: my AI-native workflow

For ten months I’ve also shipped the code for my own designs. This page shows how.

Appian Composer is Appian’s AI agent for building enterprise apps. It turns requirements and documents into a visual app plan, then generates records, process models and interfaces with AI.

Role
UX designer who ships code
Scope
40 merged PRs across 3 codebases
Timeline
10 months
Built with
AI coding tools and a skill library I curate

TL;DR

  • If I hand over working code, nobody has to rebuild my intent.
  • If a reviewer can open a link, nobody has to pull code to see it.
  • 40 merged PRs in 10 months, across 3 codebases, built with AI coding tools.

01The friction

Handoff loses things. A designer writes a spec, and engineers rebuild it from scratch. Details drop on the way, because a spec can’t carry every state and every interaction.

Review has a similar gap. A reviewer who needs to see a UI change has to pull the code and run it. Until then, the change is only code on a page.

02The workflow

Six steps. AI helps at each one.

  1. Mock it in HTML. I ask AI for a working mock with real states and real clicks, so I find problems sooner. My prototype for From prompt to working app started this way.
  2. Ask for variations. I get several versions of the same idea in one go. One version rarely shows me what the others would have.
  3. Compare them. I put them side by side and pick one, and I can say why. FIG-2 shows the idea with an invented empty state.
  4. Small change? Ship it. I write a production-ready merge request and send it. No spec, no handoff.
  5. Big change? Build a branch and a test site. I put every change on one branch, deploy a test site, and test with the real thing.
  6. Ship it with the team. Big changes become tickets, and I ship those tickets with the developers on my team. Or engineers take the branch. Ahead of Appian World 2026, Appian’s flagship event, I gave engineers a 125-file working handoff. It saved over a week of build time.

03One change, end to end

The change below is invented, so I can show every step. The steps are how I work on a real one. I write the code with AI coding tools.

The prompt

“Add an empty state to the report list. Say what the list is for. Make ‘Create report’ the main action and ‘Import a file’ a second way in. Everything must work by keyboard.”

  1. Three variants. I asked for three. They differed on one question: how much to tell someone who has never made a report. A used an icon and one button. B added a sentence and a second way in. C put a grey hint inside the list (FIG-2).
  2. Why B won. B says what the list is for and gives two ways forward, create or import. A gives one way and no reason. C looks like a row of data, so people can miss the action.
  3. Review before merge. Engineers review every merge request, like any other code change.

These checks are how I decide AI-written code is good enough to merge.

04Tools I built from friction

Reviewers had to pull code to see a UI change. So I added a Storybook preview to every branch. Now a reviewer opens a link from the merge request and checks the UI. Nobody pulls code, so a UI change is judged as a screen.

05The evidence

40 merged PRs in 10 months, across 3 codebases, built with AI coding tools. Three you can see in the product:

  • a task-plan approval view, where users approve what the agent plans to do,
  • an agent mode picker,
  • chat tables that keyboard and screen-reader users can scroll to every column.

The third one matters most to me. A spec can easily leave out a detail like that. Working code has to handle it.

06The skill library

I keep a library of skills and use them at every step. A few are my own. Most come from public sources, and credit goes to their authors. I choose them and chain them, so one step feeds the next. My contribution is the selection and the chaining, and using them on real work.

07From one designer to a team

This workflow works for me because three things are in place. To work for a whole design team, each of them has to be shared rather than personal.

  • A way to see changes without code. Per-branch Storybook previews already let reviewers open a UI change from a link. Every designer’s branch should get one by default.
  • Shared skills, not personal prompts. My skill library is mine. The steps that repeat for everyone, such as mock variations, side-by-side comparison and a merge request with visuals, should become skills the whole team runs the same way.
  • Clear review gates. Designers ship small changes; engineers review every merge request. The team needs a written line between what a designer checks before opening one and what engineering checks after.

The people part has already started. I ran two knowledge-sharing sessions with my UX team on working with AI, and built a small site for each (see them on the home page).
