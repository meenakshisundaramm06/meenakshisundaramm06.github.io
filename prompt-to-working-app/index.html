Case study 02

From prompt to working app

I built a clickable prototype to compare three ways an AI agent can turn a plan into real app objects.

Appian Composer is Appian’s AI agent for building enterprise apps. It turns requirements and documents into a visual app plan, then generates records, process models and interfaces with AI.

TL;DR

  • One sentence becomes a plan, and a plan becomes objects. I compared three ways to do the second step.
  • Bulk generation stays available for speed. Its output is held inside one story, so the model stays whole.
  • I built the interactive prototype myself, to communicate a system decision to the team.

01The problem

You type one sentence: “Build an expense management app.” The agent drafts a plan first.

The agent first drafts personas: Employee, Manager and Finance. It also drafts stories: submit an expense, review and approve, track team budget, export a monthly summary. Those produce artifacts: rough layouts, goals for each persona, workflows, business rules, a data model, and automation.

Then something has to turn all of that into real objects on the platform. That step decides how the product behaves after the first build. Each later edit has to reach the objects too, so the step runs again and again.

02Three execution models

Old: object-based. What: generate by object type. Each artifact maps one to one to a platform object. A wizard lets you pick types and generate them in bulk. Why: it is fast and simple to explain. Trade-off: stories have no say, so the objects don’t trace back to what users asked for.

Ideal: story-based. What: every story plans and builds its own objects. One story gets one task plan, and each task is one object. Why: work stays tied to the story it serves, so the app grows story by story. Trade-off: there is no bulk path, so there is no quick way to lay the foundation.

Current: story-based, with a bulk escape hatch. What: story-based by default. When speed matters, bulk still runs, but its output sits inside one foundational story. Why: people get speed when they need it, and the story model stays whole. Trade-off: one story holds a batch of objects that don’t map to individual stories.

03The bulk escape hatch

I treat the hatch as a design trade-off. Bulk generation stays available for speed. Its output is held inside one story, so the model stays whole.

The user makes the choice at the start: build foundational objects in bulk, or build from scratch, story first. If they pick bulk, one card lands on the board, “Create foundational objects”, in In Progress. Every other card is a normal story.

04Old loop versus current flow

Continuous development is where the two models split. Story-based can include a bulk run at the start. After that, every later object arrives through a story.

In the old flow, Day 0 is a prompt, then artifacts that appear on their own, then a click to generate, then objects. After every edit the loop starts again: a new artifact, another click to generate, more objects. It repeats forever. The current flow starts building, makes stories, and makes task plans. Nothing repeats.

05What the prototype argued

The prototype argued for story-based by default, with bulk kept as one foundational story. It answered the main objection, speed: a story-first product has no quick way to lay the foundation of an app, and the bulk start gives one. Because the bulk output sits inside one story, every other object still traces back to a story. FIG-14 makes the other half of the argument: object-based generation runs again after every edit, and story-based does not.

06My role

I built the interactive prototype myself, in vanilla HTML, CSS and JS, using AI coding tools. I built it to communicate a system decision to the team. I wanted people to click through the argument and see the repeat for themselves.

The prototype runs in two scenes, with a pager at the bottom to move between them.

  • Scene 01, The Plan. You type the prompt and watch the agent draft personas, stories and artifacts. The same scene then shows the three execution models as cards, tagged Old, Ideal and Current. A line between them says neither model works alone.
  • Scene 02, Old vs Current. It puts the two flows side by side and shows continuous development in each. A viewer compares them at a glance and sees the old loop repeat.

07Outcome

The prototype put the three trade-offs side by side, so the team could choose between them.

08What I learned

Bulk is the fast start and story-first is the traceable one. The current flow pays for speed with one story that holds a batch of objects, so every other object still traces to a story.
