Case study 03

Undo for AI agents

I designed how an AI agent saves and restores its edits.

Appian Composer is Appian’s AI agent for building enterprise apps. It turns requirements and documents into a visual app plan, then generates records, process models and interfaces with AI.

Role
UX designer: research, design, prototype
Team
Product, engineering, me
Timeline
Design work from Nov 2025. Shipped code for 10 months.
Built with
Figma, and an HTML/CSS/JS prototype made with AI coding tools

TL;DR

  • With manual save, the in-between AI edits can’t be restored. I proposed one version per AI change, tested it, and product and engineering adopted it.
  • For requests that touch many objects, I designed checkpoint restore. I argued for keeping the conversation. The team shipped the simpler option.
  • I built the working AI assistant prototype for the test myself.

01Saving AI edits

The problem

Developers now ask an AI assistant to change their app. It edits fast. People need to see what changed and go back.

The platform’s habit is manual save. It keeps the version count low, simplifies debugging, and speeds up pair reviews. The open question was whether AI edits should follow it.

Why manual save makes AI edits unrestorable

Take this sequence: v1, change 1, change 2, v2, change 3, change 4, change 5.

Restore only reaches changes since the last saved version: changes 3 to 5, in a temporary buffer. When the user presses Save, the buffer collapses. Those three changes become one snapshot, and nobody can restore them one by one.

The user thinks they kept every AI edit. The system kept the last snapshot. It also breaks when the AI assistant touches a second object.

The proposal

Event-based autosave: every AI change creates a new version.

Two reasons:

  1. Edits cross objects. You edit Interface A and ask the AI assistant to update the nested Interface B. The AI versions B, and A updates. No switching.
  2. Tasks span objects. Asked to “update these five rules, interfaces and expressions”, the AI must touch all of them. Autosave gives stable snapshots.

I ruled out major and minor versions. They would change versioning for every developer.

Objections, and where I stand

Version spam. Manual save already makes many versions, so AI mode adds volume to a problem that already exists. Each version has a short description and an AI or You tag, so people can scan the list.

Storage cost. Small on-premises customers may worry about paying for storage. That is the trade-off: more versions to keep, in return for every AI change being restorable.

Usability test: four findings

I built a working AI assistant prototype and tested it with developers.

  1. Mixed save modes felt natural. I feared it would feel inconsistent with manual save elsewhere. The version number on the change summary card told developers the AI assistant made a new version.
  2. They understood the version flow. A v5 made in another mode meant the next AI change became v6. Restoring an old version made a new one, such as “v3 · Restored v1”.
  3. Authorship was clear. People told AI versions from their own. I worried the AI label would make people uneasy about the work. People responded well.
  4. Unsaved edits need a guard. If someone switches into AI mode with unsaved changes, an alert above the chat field says: save or reset first. If they ignore it, the AI builds on the unsaved state.

From modal to alert

My first guard was a modal. It added too much friction, so I moved to a lighter alert.

Outcome

I ran the study and persuaded product and engineering to adopt event-based autosave: every AI change creates a new version of the object.

02Restoring checkpoints

One object became many

Saving AI edits covered an AI assistant that edits one object. The agent can build or change many in one request. Each user turn adds a checkpoint to the chat, a divider with a Restore link.

That breaks the simple model. No stable version number spans many objects, so restore must undo a set of them together.

The restore dialog

Restore opens a dialog. It says restoring removes later changes and clears the conversation context. It lists each affected object with its diff, and warns that references elsewhere may need manual fixes.

Four options

Four restore options and their trade-offs
OptionWhat it doesProCon
AReverts objects, erases later conversationPredictable, no partial restoresLoses reasoning; feels destructive
BReverts objects, keeps conversation, marks checkpoint “restored”, shows a brief confirmationLight; keeps the reasoning trailUsers may forget a restore after a long gap
CB plus a system message in chatVisible in historyClutter; long multi-object diffs; hard to scale
DC, with no re-restoreAvoids state explosion and nested undoDisabled buttons with no reason confuse people

My pick: B

B corrects the objects and keeps the reasoning trail, with a brief confirmation instead of a permanent message. Cline and GitHub Copilot treat restore the same way, as a system action rather than a chat message. The cost: someone may forget a restore happened.

I passed on C because I couldn’t word its message across many objects, and the diffs run long. Engineering preferred D for state simplicity. I worried about locked buttons with no reason given.

What shipped: A

The team shipped A. For a first version, that was a fair call. It is technically simple and easy to understand, with no partial restores. The dialog warns about the cleared conversation before users commit.

What I’d watch next

  • Whether people lose context. A restore erases the “why did we get here” trail.
  • Whether Restore feels too heavy when someone only wanted to undo object changes.

If either shows up, I will argue for B.

03What I learned

I changed the team’s mind with a working prototype. When my pick (B) lost to the simpler A, the team shipped A and I wrote down what to watch.
